Stage 01 · Discover

Find recurring work worth automating

Deliverable: candidate task list

Start with work people already repeat. AI can help inventory and screen candidate tasks; you confirm frequency, inputs, rules, acceptance criteria and risk boundaries.

Process

  1. List daily, weekly and recurring on-demand tasks.
  2. Screen each across five dimensions: frequency, input, rules, acceptance and risk.
  3. Choose one or two high-frequency tasks.
  4. Define the role in one sentence: “When it receives X, it does Y and sends the result to Z.”

Prompt 1 · Discover recurring work

Ask one question at a time, summarize briefly and finish with a structured task list.

You are a work-efficiency specialist. Help me identify the tasks I repeat each week through a conversation. Rules: - Ask only one question at a time. - After each answer, summarize it in a short description (no more than 15 words). - Ask in order: the first thing I do after opening my computer; tasks I do daily or every other day; weekly deliverables; tedious repeated work; tasks other people often ask me to do. - After five rounds, create a recurring-work list with task, estimated time or frequency, and automation potential (✅ / ❌ / 🤔). - Recommend one or two high-frequency tasks for further screening. Start with the first question.
A task marked as an automation candidate is not automatically approved for unsupervised operation.
Stage 02 · Specify

Create the Agent role card

Deliverable: 01-role-card.md

A clear role card says who the Agent serves, what problem it solves, what it receives, how it works, what it delivers and when a person must step in.

Input→Actions→Output→Standards→Fallback

What the card contains

  • Role name and one-sentence definition.
  • Inputs: content, source and format.
  • Three to eight concrete processing actions.
  • Outputs: content, destination and format.
  • Success criteria and signs of failure.
  • Escalation conditions, review points and out-of-scope work.
You are an AI Agent architect. Help me design a complete role card for this recurring task: [task name]. Current one-sentence definition: [when it receives what input, it automatically does what, and sends the result where]. Interview me one question at a time. Wait for each answer before asking the next. Ask follow-up questions when details are vague. Clarify in order: (1) inputs, sources and formats; (2) processing steps; (3) outputs, destination and format; (4) success and failure criteria; (5) when a person must intervene and where to review; (6) three to five things the Agent must not do. Then create a role card with: role name, one-sentence definition, inputs, actions, outputs, success criteria, human fallback and current exclusions. Ask what needs revision and update it until I confirm.
Do not invent missing facts. Ask the owner whenever a source, acceptance criterion or boundary is unclear.
Stage 03 · Structure

Turn experience into an executable workflow

Deliverables: 02-workflow-card.md · 03-flowchart.md

Break the task into small steps and uncover the reasoning behind each decision. Then translate the human goal into Agent behavior instead of copying a person's mouse actions.

Discover and confirm

  1. Read the approved role card; do not fill gaps from chat memory.
  2. List every manual step (5–12), including small actions.
  3. Estimate time; have the owner correct false steps and add missing ones.
  4. For each decision, ask why, which signals matter, what exceptions exist and where a newcomer may go wrong.

Design for an Agent

  • Translate opening pages, clicking buttons, copying and downloading into suitable capabilities.
  • Label requirements using RFC 2119: MUST, SHOULD, MAY and MUST NOT.
  • Describe each step with an action, judgment rule and exception handling.
  • Define verifiable success criteria, failure handling and human review points.
  • Draw a Mermaid flowchart TD with decision branches and fallback nodes.
You are an Agent workflow coach. Help me uncover my real decision rules; do not answer for me. Discuss one step at a time and ask one question per turn. Follow up until the decision rule is clear: Why do I do this? Which signals guide me? When do I change approach? What exceptions or past mistakes matter? Where might a newcomer go wrong? When clear, summarize: Judgment / Evidence / An actionable Agent rule / Exceptions. Then move to the next step. If something is unknown, ask me instead of guessing. After all steps are confirmed, synthesize an Agent workflow with trigger conditions, steps labeled MUST/SHOULD/MAY/MUST NOT, action, decision rule, exceptions, success criteria, failure handling and human fallback. Create a Mermaid flowchart TD only after I approve the workflow.
Save only the confirmed final version. Preserve the Stage 02 role card. If a target file already exists, review what would be replaced before overwriting it.
Stage 04 · Profile

Write the Hermes Agent “brain”

Deliverables: 04-profile.md + runtime Profile

A course backup and the Profile Hermes actually reads serve different purposes. Verify the supported setup, real path and recognition status before writing.

Ten Profile sections

  1. Work objective, input scope and workflow.
  2. Output and quality standards; self-check rules.
  3. Exception handling and human fallback.
  4. Prohibited actions.
  5. Pre-completion checklist.

Safe sequence

  1. Verify how Hermes supports Profiles and where it reads them.
  2. Check that the role card and workflow are complete and readable.
  3. Prepare the Profile for owner review before writing files.
  4. After approval, save a course copy and sync the runtime Profile.
  5. Read both back, compare them and verify Hermes recognizes the Profile.
Do not guess the path. Do not treat 04-profile.md as the runtime file. Do not create a second Profile when continuing an existing Agent.
Using the approved role card and workflow, draft a complete Hermes Agent Profile with: objective; input scope; workflow; output standards; quality standards; self-checks; exception handling; human fallback; prohibited actions; completion checklist. First send me the draft for review. Do not write any files yet. Keep the role card and workflow unchanged. After I approve, save a course copy as 04-profile.md and sync the exact runtime Profile path we verified. Then check that both files exist, their contents match and Hermes recognizes the Profile. If the runtime path or recognition status is unverified, stop and ask me.
Stage 05 · Integrate

Connect the right tools and data

Deliverable: verified integrations

Use the workflow to identify tools the Agent actually needs. The guide names Hermes, Feishu/Lark CLI, bots, documents, spreadsheets and Base tables as examples; every permission should match a task.

Items covered in the guide

  • Configure the Agent with its approved Profile.
  • Connect Hermes to Feishu and verify private and group chats.
  • List required external tools with installation guidance.
  • Review permissions to create, edit or delete documents and tables.

Control points

  • Verify each permission with an observable, low-risk action.
  • Grant only what the workflow requires.
  • Confirm write or delete actions with the owner.
  • Pause and report authentication, permission or data ambiguity.
This guide describes an architecture; it does not grant access or connect APIs. The public showcase in Stage 06 must stay separate from private APIs and data.
Stage 06 · Validate & deliver

Test, document and showcase the Agent

Deliverables: user guide + showcase page

Test three pieces of content with different sizes or contexts. Record actual results and publish only capability claims that have been verified.

User guide

  • What the Agent is and which manual work it reduces.
  • What Codex, Hermes and Feishu CLI each do.
  • Inputs, trigger conditions and usage steps.
  • Real output examples and recent run evidence.
  • Limits, escalation cases and known issues.

Three test runs

  1. A small case with clean input.
  2. A larger or structurally complex case.
  3. An exception case with missing or unclear information.

Compare output with the acceptance criteria, log failures and improve the workflow before handoff.

A safe public showcase can explain

Function→Workflow→Standards→Capabilities & limits→Approved examples
The guide calls for a realistic-looking showcase that reveals no permissions or private data. It must not connect to an API or let visitors invoke the Agent. This page is informational and its prompts are examples.
Safety boundaries

Explain the capability; protect the system

Showcase only · no execution

Suitable for public display

  • Agent objectives and supported tasks.
  • High-level workflow and quality standards.
  • Known limits and situations requiring human review.
  • Prompt examples cleaned of personal details.
  • Mock or explicitly approved output examples.

Keep off the page

  • API keys, tokens, cookies and login details.
  • Personal data, private Feishu files or internal links.
  • Local Profile paths, logs or sensitive configuration.
  • Buttons or endpoints that invoke the live Agent.
  • Unmeasured claims about results or time saved.
This guide is adapted from the Agent architecture document. Prompt cards are instructional examples, not proof that an Agent has run. Use only examples approved for public sharing.
